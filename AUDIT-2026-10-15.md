## Medium

### 1. Job timestamps are wrong by the local UTC offset
`chessme/app/jobs.py:15-16` (`iso`), used by `to_out` (line 19-22) for `GET /api/jobs`, the job responses and every `/api/events` message.

The columns are `DateTime(timezone=True)` but SQLite stores no zone: SQLAlchemy returns **naive** datetimes holding the UTC values that were written.
`iso()` calls `d.astimezone(timezone.utc)` on them, and `astimezone` on a naive datetime assumes *local* time. So everything read back from the
database is shifted by the machine's offset. (Only the very first message, built from the in-memory object right after the insert, is right.) The
unit tests pass because CI runs in UTC.

**Reproduced** (`JobManager.submit`, then `get`, under three time zones; the real UTC "now" was 08:04):
```
TZ=UTC               createdAt 2026-10-15T08:04:52+00:00   (correct)
TZ=America/New_York  createdAt 2026-10-15T12:04:53+00:00   (4 h late)
TZ=Asia/Kolkata      createdAt 2026-10-15T02:34:54+00:00   (5.5 h early)
```
**Why it matters:** the Activity page will show wrong "started/finished" times, and "finished before it started" can appear around DST changes.
**Fix:** treat naive values as UTC (`d.replace(tzinfo=timezone.utc) if d.tzinfo is None else d`), or give the models a `TypeDecorator` that always
returns aware UTC. Add a test that runs `iso` with `TZ` set to a non-UTC zone.

### 2. Same-day games are listed oldest first
`chessme/app/services/games.py:57` (`played_at` keeps the date only, `UTCTime` is dropped) and `:133` (`ORDER BY played_at DESC, created_at DESC`); the
same ordering is in `services/stats.py:29` and `analysis_job.py:16`.

Importers deliver games newest first, so on one day the newest game gets the smallest `created_at`; the tiebreak `created_at DESC` then puts the
**oldest** game of that day first. **Reproduced** (three games of 2026-10-14 at 20:00, 12:00 and 09:00, inserted in the order Lichess returns them):
```
library order (newest first expected: evening, noon, morning): ['morning', 'noon', 'evening']
```
**Why it matters:** the home page's "learn from your last game", the "recent 20 / previous 20" accuracy windows and the accuracy series
(`stats.compute` takes `acc[:RECENT]`) and `unanalysed_ids(limit)` ("newest first") are all wrong for anyone who plays several games a day.
**Fix:** store the time (`played_at` as `2026-10-14T20:00:00Z`, or a second column `played_ts`) and sort on it; keep the date-only value for display.

### 3. The API is unauthenticated: a local caller can run any executable
`chessme/app/routers/api.py:200-207` (`PATCH /api/settings` accepts any executable file as `engine_path`) and `chessme/app/workspace.py:20-23`
(`engine_name` runs `[path]` with `uci\nquit\n`), called on every `GET /api/workspace`.

`LocalOnly` (`security.py`) protects against *browsers* (Host and Origin checks, which I verified work). It does not protect against another
process or another user on the same machine, because there is no secret. **Reproduced:**
```
PATCH /api/settings {"engine_path": "<script that writes a marker file>"}  -> 200
GET   /api/workspace                                                      -> 200, engine detail "Evil"
marker file written: True
```
**Why it matters:** on a shared computer (or with any local malware or a second local web app) this is "run a program as the app's user" with two
unauthenticated requests. It is also a GET that spawns a process.
**Fix:** generate a random token at start (printed in the URL the app opens, kept in an `HttpOnly` cookie or a header the page adds) and require it on
every request; or at least (a) validate `engine_path` only in the PATCH, with an `id name` handshake and a 3 s timeout, (b) store the result, and
(c) never execute anything on a GET.

### 4. `chessme coach` has no Host or Origin check
`chessme/coach/server.py:328-401` (`make_handler`, `do_POST`); started by `cmd_coach`.

The new FastAPI app refuses foreign Host and Origin headers; the older coach server does not, and it parses the body as JSON whatever the
`Content-Type`. **Reproduced** (a request with `Origin: https://evil.example`, `Host: evil.example:8765` and `Content-Type: text/plain`):
```
POST /api/profile  -> 200 {"moves": 0, "findings": [], "games": 0, "sentences": [...]}
POST /api/drills   -> 200 {"total": 0, "due": 0, "boxes": [...]}
```
**Why it matters:** (a) any web page you visit can POST `text/plain` JSON to `127.0.0.1:8765` without a preflight: start Stockfish analyses
(`/api/start`, CPU), trigger Lichess/Chess.com fetches (`/api/games`), and write reviewed-game files into the coach data folder (`_keep`); (b) with DNS
rebinding the page can also *read* the answers (weakness profile, reviewed games, drills).
**Fix:** reuse `security.LocalOnly`'s checks in `do_POST`/`do_GET` (Host in {127.0.0.1:port, localhost:port}; if `Origin` is present it must equal ours),
and require `Content-Type: application/json`. Smaller: a negative `Content-Length` (line 349) makes `rfile.read(-1)` block until the client closes.

### 5. `!elo` patch: a chat message of just `!` raises `IndexError`
`tools/patch_lichess_bot_chat.py:35` (the generated branch `elif cmd.split()[0] == "elo":`).

For the chat text `!` (or `! `, or `!` plus spaces) the command string is empty, the earlier `if/elif` branches do not match, and `"".split()[0]`
raises. **Reproduced** on the repository's own stand-in for lichess-bot's `lib/conversation.py` (`tests/unit/test_lichess_bot_chat_patch.py`):
```
'!'     -> EXCEPTION IndexError list index out of range
'! '    -> EXCEPTION IndexError list index out of range
'!   '  -> EXCEPTION IndexError list index out of range
'!elo'  -> ["I'm playing at about 1500 Elo. ..."]
```
**Why it matters:** the sender is the game's opponent; an exception in the chat handler runs inside lichess-bot's game loop. I did not read the real
upstream code (the `bot/` folder is local-only and out of scope), so the exact effect (game thread ends, bot stops moving) is from the stand-in's shape.
**Fix:** `elif cmd.split()[:1] == ["elo"]:` (or `cmd.startswith("elo") and cmd[3:4] in ("", " ")`), and add `'!'` / `'! '` to the test. Also
`arg.isdigit()` accepts characters like `²`, for which `int(arg)` raises `ValueError`: use `arg.isascii() and arg.isdigit()`.

### 6. `pip install .` gives an app that cannot start and has no UI
`pyproject.toml:7` lists `requests, pyyaml, chess, numpy, torch, zstandard` only. `chessme app` imports `fastapi`, `uvicorn`, `sqlalchemy`, `alembic`
(and pydantic through FastAPI); they appear only in `requirements.txt`. The package data entry `"chessme.app" = [..., "static/**/*"]` has no build step
that copies `frontend/dist` into `chessme/app/static`, and `main.static_dir()` (`chessme/app/main.py:18`) otherwise looks for
`<site-packages>/frontend/dist`, which does not exist for an installed package.
**Why it matters:** the same class as the previous audit's #13 (installed CLI broken). **From reading** (I installed nothing).
**Fix:** add the dependencies (or an `app` extra), pin like `requirements.txt`, and copy the built frontend into `chessme/app/static` before building a
wheel (a small `setup.py` hook or a documented `make wheel`).

## Low

### 7. Import jobs: concurrency and cancellation
`chessme/app/jobs.py:48` (two workers, no per-site lock); `chessme/app/importers.py:45` (`time.sleep(65)` on a 429); `importers.py:116-141`
(`import_stream`); `jobs.py:140-143` (`shutdown`).
- Two Lichess imports (two user names, or a double click) run in parallel on the two workers. The project rule (and Lichess) is one request at a time
  per address, and the Lichess bot shares that address.
- The 65 s wait for a 429 cannot be cancelled (`ctx.check()` is only called per game), and `ThreadPoolExecutor` threads are joined at interpreter exit:
  a stop during the wait takes a minute.
- `import_stream` keeps one session with up to 24 uncommitted games while the generator waits for the network (Chess.com: a request and a 0.3 s sleep
  per archive). SQLite's write lock is held meanwhile; another writer (a second job's status update, `PATCH /api/settings`) fails with "database is
  locked" after the default 5 s if the stream stalls.
- `shutdown` iterates `self._cancel.values()` while a worker may `pop` from it: a possible "dictionary changed size during iteration" at exit.
**From reading.** **Fix:** one lock (or one single-worker executor) per site; `ctx.sleep(seconds)` that waits on the cancel event; commit before blocking
on the network (or per game); `for ev in list(self._cancel.values())`.

### 8. Ctrl-C does not stop the server while a tab is connected
`chessme/app/routers/api.py:172-188` (`/api/events` streams until the client disconnects; uvicorn waits for open streaming responses).
**Reproduced:** started `python -m chessme app --port <p>`, opened `GET /api/events` on a raw socket, sent SIGINT: the process was **still running 20 s
later**. Any open browser tab holds this stream, so the first Ctrl-C appears to do nothing and a second one is needed (jobs left "running" are marked
failed on the next start, so no data is lost).
**Fix:** `uvicorn.run(..., timeout_graceful_shutdown=2)`, and have the stream also stop when the app is shutting down (a flag set in the lifespan, checked
in the loop).

### 9. A fixed 60 s search timeout against a 50M-node setting
`chessme/app/schemas.py:81` (`nodes` up to 50,000,000), `chessme/analysis/runner.py:137` calls `engine.go(...)` with the default `timeout=60`
(`chessme/uci_client.py:105`). On timeout `_readline` kills the engine and the whole analysis job fails ("timed out waiting for the engine"). At one
thread and about 1M nodes/s, 50M nodes is about 50 s on a fast machine and over 60 s on a loaded one; the same holds for `hash_mb` up to 65,536 on a
RAM-limited laptop. **From reading.** **Fix:** pass `timeout=max(60, nodes / 200_000)` (or make `engine_search` derive it), and lower the setting's
maximum or warn.

### 10. The sparkline loses the end of the game
`chessme/app/services/games.py:91-95` (`spark`): `step = max(1, len(moves) // 40)` then `[: n + 1]`. For 41 to 79 moves `step` is 1 and the list is cut to
the first 41 points. **Reproduced:**
```
60 plies  -> 41 points, last point is ply 40 of 59
79 plies  -> 41 points, last point is ply 40 of 78
100 plies -> 41 points, last point is ply 80 of 99
```
So a 60-move game's sparkline ends at move 20 (and 100 plies at ply 80). **Fix:** sample indices with `np.linspace(0, len-1, n)` (always include the last
point).

### 11. `%` in the data folder breaks the migration
`chessme/app/db.py:27` passes the SQLite URL through `Config.set_main_option`, which interpolates `%`. **Reproduced:** data folder `my 100% data` ->
`ValueError: invalid interpolation syntax in 'sqlite:////.../my 100% data/m.db'`, so the app does not start. **Fix:**
`cfg.set_main_option("sqlalchemy.url", url.replace("%", "%%"))`.

### 12. Review keys hijack Cmd/Ctrl+F
`frontend/src/features/review/Review.tsx:59-72`: `onKey` matches `e.key` only; modifier keys are not excluded and `e.preventDefault()` runs.
**Reproduced** (Playwright, `Meta+f` on `/review/s03`): the key event arrives with `metaKey: true` and `defaultPrevented: true`, i.e. the browser's Find is
blocked and the board is flipped. `Ctrl+B` and `Alt+ArrowLeft` (history back) are handled by the same code (I did not log those two events). **Fix:** `if (e.metaKey || e.ctrlKey || e.altKey) return;`
at the top of the handler.

### 13. Retry state survives leaving the retry
`frontend/src/features/review/Review.tsx:78` (`goto` only calls `setRetryOn(false)`) and `useRetry.tsx:25-30` (`go`/`exit` reset `k`, `status`, `fen`,
but only `exit()` is called, from the panel's own buttons). **Reproduced:** retry, press Reveal (status "revealed"), click a move in the Moves tab,
press "Retry your mistakes" again: the panel still reads "The better move was Rad1; you played Nf6+" with "Next mistake" instead of starting with
"Find a better move". **Fix:** reset the hook state when `active` turns false (an effect on `active`), or call `go(0)` from `goto`.

### 14. The board cannot be used with the keyboard
`frontend/src/board/Board.tsx:166`: `role="application"` with only pointer handlers; **Reproduced:** `tabIndex` is `-1`. The review's stated keyboard
support (docs/ui.md) covers stepping, not moving; the main learning loop (retry) needs a mouse or touch. Related: `Library.tsx` rows use
`role="row"` / `rowgroup` without a table or grid parent, and `Shell.tsx` nests a `<button>` inside the Activity `<a>`.
**Fix:** make the board focusable, with arrow-key square navigation and Enter/Space to select/drop, announce the selection in the `aria-live` region; use a
real `grid`/`table` role set or plain `<ul>`.

### 15. Settings is unreachable on narrow screens
`frontend/src/components/Shell.tsx:31` (`NAV.slice(0, 5)` for the bottom bar) and `:36` (the Settings link is `max-md:hidden`). **Reproduced** (viewport
600 px wide): visible navigation links are `/`, `/library`, `/coach`, `/play`, `/explorer`; nothing leads to `/settings`. **Fix:** put Settings in the
bottom bar or a menu on small screens.

### 16. No error boundary; "From Position" games
`frontend/src/App.tsx:3` (router without `errorElement`); `frontend/src/lib/game.ts:26-34` (`fensFromUci` starts from the standard position and
`chess.js` throws on an illegal move); `chessme/app/importers.py:106` accepts `Variant` "From Position" (and the stored PGN keeps the `FEN` tag).
The API (`GameDetail`) has no start position, `services/stats.py` and `coach/profile.player_rows` assume the standard start, and the analysis
(`analyse_game`) uses `game.board()` and therefore *does* honour the FEN. So a game from a custom position is analysed correctly, then the review page
throws while rendering and (without a boundary) shows a blank page. Latent at `a23a256` (the frontend still reads sample data), real once it reads the
API. **From reading.** **Fix:** either skip such games in `store_pgn` or return `start_fen` and use it in `fensFromUci`/`mistakes` parity; add an
`errorElement` with a "back to the library" link.

### 17. NaN poisoning in the error profile
`chessme/humanlike/errors.py:60` says regimes with too few tail positions "get NaN: no correction possible", but `model_values` (`:74`)
computes `(1 - t) * v + t * tail[k]`, and `0 * NaN` is NaN. **Reproduced** (400 synthetic positions, 10 of them in a regime with fewer than 20 tail
positions):
```
tail mean-loss stand-ins: {'unknown': nan, '30s+': 0.065}
nan positions in model mean loss: 10
all-positions model mean (cluster bootstrap): (nan, nan, nan)
```
With the real sample sizes (4,000 per regime) the minimum of 20 is met, so production runs are probably unaffected, but a small sample or a regime
without clocks turns every pooled number into NaN silently (`blunders.type_rates` handles the same case with zeros; `errors` does not).
**Fix:** `np.where(np.isnan(tail[k]), v, (1 - t) * v + t * tail[k])` (no correction, as documented), and report the number of uncorrected positions.

### 18. "All judged positions" is a quota mix
`chessme/cli.py:1585` (and `humanlike-judge`, `cli.py:1526-1560`): the judged sample takes `--per-regime` positions from each of three clock regimes, so
the pooled row "all judged positions" weights low-clock positions about as much as ample-clock ones. Its model-minus-human differences are valid (paired),
but its *levels* (human blunder rate, mean loss) are not population rates, and the report text does not say so. **From reading.** **Fix:** say so in the
report header, or weight the pooled row by the regimes' shares in the full test set.

### 21. Supply chain
- Notebooks install `python-chess numpy pyyaml requests zstandard` unpinned, while the repository pins `chess==1.11.2` etc.; they clone Maia-3/Maia-2

**Fix:** pin versions in the notebooks (or install from a lock file), compare the digest to a constant, `curl -fsSL`; save adapters as

### 22. Chain scripts that never give up

### 23. Smaller app issues (all from reading)

  get a CSP. Another site can frame `http://127.0.0.1:8765` (clickjacking of imports/deletes). Add `frame-ancestors 'none'` and a strict CSP.
- (Commit `21307e3`, outside the baseline) `--dev` now trusts `localhost:5173-5180` as origins; any other local dev server on those ports can then
  call the API.
